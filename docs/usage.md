# Using the library

[Install and browse skills](../README.md) · [How the library fits together](architecture.md)

## Choose a workflow

For a feature, bug fix, refactor, investigation, or performance task, start with `pstack-mode`. Give it a goal, observable completion criteria, required proof, and constraints, and it chooses and drives a playbook. It plans through code: a design question it could settle by running something gets a prototype or an `architect` sketch rather than a written plan or a question to you. Invoke it explicitly for the current conversation, or pick an option that names it, such as the one `next-options` offers when an answer's next step changes code. Installation and individual helper invocations do not activate the mode, and nothing routes prompts into it automatically; [ADR 0007](adr/0007-keep-pstack-mode-explicit-and-offer-it.md) records why.

To refactor a whole codebase in one pass, rather than one area of it, invoke `untangle-codebase` by name.

When an effort needs agreement first, start the Matt flow with `grill-with-docs`, then choose by how many sessions the build needs, as Matt Pocock does. A build that fits one session goes straight to `pstack-mode`. One that spans sessions, or that other people will pick up from a tracker, goes through `to-spec` and `to-tickets` to `implement-spec`, which runs each ticket through a `pstack-mode` playbook; a ticket graph needing a persistent T3 project thread can go to `coordinator` instead, with separate PRs or one combined PR as requested. A huge effort whose way is still unclear starts with `wayfinder`, which charts its open decisions on the tracker before any spec. Skip stages that are already settled; `implement` handles a smaller agreed piece of work in the current session, and `retro` reviews a finished session. Relevant Pstack principles apply automatically throughout the Matt flow, including implementation and review.

Both paths end implementation with `review-loop`: the other vendor's model reviews the change alongside the main model's own reviewers, and the agent fixes what holds and re-reviews until clean. A small diff away from sensitive paths gets only the other vendor's review in round 1. Invoke `review-loop` directly for a second opinion on any branch or PR, or on a plan when you want one. Every PR body written through `pr` opens its Evidence with the review status, and a UI change without a screenshot says it was not verified and why.

For a project of several PRs or research questions in T3 Code, ask `coordinator` to run it from the current thread. It pins the thread, starts a worker per unit, each running a `pstack-mode` playbook in its own worktree, watches their PRs, and brings you one decision at a time; you answer only there. For a large feature that must merge together, say: “Use coordinator, split implementation into tickets, and deliver one final PR.” It keeps every ticket worker visible in that same thread and assigns one integrator to assemble and verify the feature before your final merge approval. `/implement-spec` remains useful when you already have a spec and ticket graph and want its direct execution flow. Outside T3 Code, `pstack-mode`'s Orchestrate playbook runs such a program.

Both paths use the same [principles, shared owners, and project artifacts](architecture.md#how-the-workflows-compose). You do not need to remember every helper. Use `pstack-help` for routing or invoke a specialist directly when you know which one you need.

## Configuration and prerequisites

Existing project conventions take precedence. Use `/setup-matt-pocock-skills` to establish or reconcile shared domain-document and issue-tracker guidance. `/pstack-setup` is optional personal configuration for model roles, effort, review providers, and source locations; omitted options use the adaptation's defaults. These setup skills change configuration only when invoked for that purpose.

Capability-dependent workflows declare their prerequisites. Bun-backed Pstack tools prepare a runtime cache outside installed source; the `review-loop` and `next-options` scripts run on Node 24 or newer; `ketchup-video` needs a video encoder such as `ffmpeg` to render and check its frames. `setup-agent-sign-in` drives the `agent-browser` CLI, and `swarm`'s Computer Use route falls back to it; the CLI and its skill install from `vercel-labs/agent-browser`, outside this library. Cross-vendor review runs the other vendor's model, Codex from Claude and Claude Opus from Codex, with an explicit model, effort, and speed: as a T3 child task in T3 Code, and through the other authenticated CLI elsewhere. Codex delegates run in fast mode while Codex usage is on pace for its next reset, with a day's lead allowed, or banked resets that last long enough cover the gap, and at standard speed otherwise. Below 5%, reviews go to a same-vendor critic, and the report labels that fallback coverage. Claude delegates run at standard speed. Claude hands checks that need Computer Use to Codex, which needs Codex's Computer Use plugin and macOS Screen Recording and Accessibility permissions; off a Mac, the check runs on a Mac that the session's T3 Code server links to and reaches, when this thread and the link allow full access. Pstack's trivial edits use Sonnet in Claude Code, while exploration, investigation, tooling review, check runs, code, judgment, and synthesis keep the main model. `/pstack-setup` can override any of these roles, the counterpart's model, effort, and speed, the pace slack, and the fallback threshold. The webhook UI needs an existing receiver and defaults to localhost; it does not provide an agent execution service.

`/next-options` ends replies with what comes next for the current conversation: one plain line when the agent carries on by itself, or one or two lettered options when the user decides. To load it in every Claude Code and Codex session, ask it to install its SessionStart hook; that changes host settings only on request. `/reply-shape` lays out the rest of each reply as a glance, a one-line headline, one fact table of labelled rows, a view only for what the table can't hold, and one fold, and loads through the same hook.

## Install and update

Use the [complete-library install](../README.md#install). Skills CLI does not install dependencies transitively; partial installs need the listed companions. To try unpublished changes, run that command from the repository root with `.` as the source.

Installations are snapshots. After changes merge, rerun the complete install to refresh your selected agents and discover new skills. Install from this repository rather than overwriting its adaptations with same-named upstream skills. A repository update does not refresh global installations automatically. To check them against `main`, run `git fetch origin main`, then `python3 scripts/check-installs.py` from this repository. It reports stale, missing, unknown, and retired installs, same-named skills from other sources, and entries in `~/.claude/skills` that load something other than the shared install. When a skill is stale, missing, or unknown, it also prints the complete install, which runs without prompts when the lock records the agents you last chose.

For source upkeep, use `/maintain-skills` and the [repository maintenance guide](../skills/agents/maintain-skills/MAINTENANCE.md). Upstream runs adopt upstream changes while keeping the library's local adaptations; audits also recheck skills against current tools and conventions. This is separate from refreshing installed copies.

To tune the workflow from how it is used, `/usage-review` measures the owner's T3 Code threads, follows up on its earlier changes by their metric contracts, and opens at most one draft PR. A weekly T3 scheduled task in this repository's project runs it from the default branch.

## Agent compatibility

Use `$skill-name` in Codex and `/skill-name` in Claude Code. Native delegation and hook adapters target these two hosts. Skills CLI offers other agents too; workflows that depend on host-specific tools need a compatible integration. Agent selection during installation does not add that integration. The [validation history](reviews/README.md) records exercised branches and remaining limits.
