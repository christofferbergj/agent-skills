# Maintain an owned Pstack adaptation

The initial adaptation covers the 54 registered skills in upstream Pstack and their supporting playbooks, prompts, and scripts as an owned adaptation for Codex and Claude Code. The three dormant Benny automation workflows are outside this scope.

Preserve each workflow's purpose and evidence requirements. Adapt worker counts, model choices, and continuous loops to the task, available capabilities, and budget.

Namespace new skills as `pstack-*`, reuse the existing identical `bro` skill, and maintain an upstream-to-local mapping. This prevents collisions with other installed skills and makes upstream comparisons traceable. The revision below drops the prefix.

Proceed autonomously within agreed scope. Pause when scope or an approved interface changes, or repeated failures require a decision. Deliver draft pull requests by default and honor existing authorization for further actions.

## Revisions

- **2026-10-26, upstream names.** Pstack skills now keep their upstream names, as Matt Pocock's, Thermos, and the other sources do. The prefix had come to suggest a skill works only in Pstack mode, while each one works alone and several serve the whole library: `/swarm` runs `/review-loop`'s counterpart, and Matt's flow invokes `/principles` and the principles. It also made every upstream sync rewrite each cross-reference. `suite.json` already traces each skill to its upstream, and of the 58 upstream names only `tdd` collides with an installed skill, Matt Pocock's, so Pstack's stays `pstack-tdd`. The entrypoints stay `pstack-mode`, `pstack-help`, and `pstack-setup`, because upstream names two of them after the author's handle and the three share the suite's name. The first-party selector `pstack-principles` became `principles`. The adaptation contract's names rule now covers every source, and the catalog check rejects a rename without a recorded reason.
- **2026-10-27, model roles.** The adaptation had translated upstream's per-role model table into "the roles /pstack-setup configures", but only the counterpart and Computer Use roles could be configured, so every other spawn ran on the session's model. Upstream runs code delegates, explorers, investigators, tooling review, and verification workers on a fast model, and keeps its strongest model for the hardest changes, judgment, and synthesis. The user leads with Claude Opus and accepts Sonnet or another cheaper model for helper agents such as exploration. So `/swarm`'s `target.py` now resolves upstream's roles by their labels: fast roles run on the host's fast model, Sonnet in Claude Code, and the rest keep the session's model. Code delegates depart from upstream and stay on the main model, because the user named helper agents, not code writers, as the place to save. Panels such as `/arena`'s runners seat the session's model and the counterpart, which keeps upstream's two model families. Codex keeps its own model for fast roles until the user configures one, since no Codex fast model was agreed. `/pstack-setup` overrides any role.
- **2026-10-27, speed.** The user puts performance and speed ahead of cost. Codex delegates, native ones included, now run in fast mode while Codex usage stays at or above the 40% threshold from ADR 0004's usage-aware targets, because the user does not use up the Codex plan. Claude delegates never use fast mode, because Claude is the main agent and fast mode would spend its usage. This replaces upstream's rule of fast mode only when a job is urgent.
- **2026-10-31, borrowed fast roles.** A blind bakeoff reran three real read-only briefs, an architecture scan, a module deep-dive, and a dependency sweep, on Sonnet 5.5, Opus 5.5, and GPT-6.1 Sol at `xhigh`, and three Opus and three GPT judges checked every report against the code. Sonnet ranked last in all nine verdicts. Each judge family ranked its own model first and the other second. GPT made the fewest verified errors and finished 1.5× faster than Opus at standard speed, 1.8× in fast mode; Opus covered the most ground ([evidence](../reviews/2026-10-31-explorer-model-bakeoff.md)). The user now puts quality first, then whole-task speed, then cost, and wants both subscriptions used. So a Claude Code coordinator's fast roles other than `fast-code` can borrow the counterpart, configured per role, while Codex usage is on pace for its window and at least the fast threshold is left, and otherwise run from the role's own entry, such as Opus at high effort. A pace rule rather than a fixed cap, because the Codex plan now runs closer to its weekly limit: borrowed roles take only capacity the week has accrued and stop before reviews would leave fast mode. They take only the T3 route, because the CLI wrapper blocks the web and MCP tools explorers and investigators need. `fast-code` stays native because it edits the coordinator's checkout. This restores upstream's other-family fast model for these roles. Roles without a `counterpart` keep their defaults.
