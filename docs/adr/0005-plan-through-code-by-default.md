# Plan through code by default

Pstack's author plans through code rather than on paper ([The Complete Guide to pstack Pt. 2](https://x.com/poteto/article/2097732320606507506)). Open design questions get prototypes and `/architect` sketches, and a written plan comes only after the design settles. The guide also argues against adversarial review of abstract plans, because reviewers invent theoretical risks that no code supports. A 2026-10-27 review against the guide found the library had inherited the opposite default from Matt Pocock's flow. The README sent every feature through an interview, a spec, and tickets. `/grilling` put every design question to the user, and `/next-options` offered a counterpart review of each new spec.

The user rarely writes specs and tickets now but wants to keep that option. So `pstack-mode` becomes the default start for building and fixing, and Matt's flow stays the choice for an effort that should be written down and split into tickets first. `pstack-mode` still reuses an accepted spec and ticket graph.

Within Matt's flow, a design question that running something could settle is a fact rather than the user's call. `/grilling` answers it with a throwaway sketch, through `/design-prototype` or a measuring script, and reports the result as a settled decision the user can overturn. A question about how something should look is still the user's, but it is asked with `/design-prototype`'s variants in hand. Product and preference calls stay with the user, and so does the final confirmation of shared understanding.

`/review-loop` still reviews a plan when the user asks, and it remains the final review of every implementation. `/next-options` no longer offers a plan review as the next step after `/to-spec`; it offers a prototype for any open question a run could settle. A plan review names a risk only with the code path or observed behavior that shows it, and the coordinator drops a plan risk that nothing cited supports.
