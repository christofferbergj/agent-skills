# Keep pstack-mode explicit and offer it when an answer turns into a change

A 2026-11-02 review asked whether `pstack-mode` should start automatically by prompt or work type. It classified the owner's 340 top-level T3 Code threads from the four weeks after they moved to T3 and tested routers against hindsight labels of the route each thread needed. When the owner typed `/pstack-mode` in a thread's first message, the label agreed in about 119 of 125 threads. On the 100 first messages after the mode shipped that named no skill, the owner's own choice matched in 55, a rule-based router in 57, and a blind model router in 63; the labels and that router come from the same model family, which inflates its lead. Its gain came to about three changed outcomes per 100 such threads, at the cost of about ten needless full runs of 10 to 17 subagents each. The failures that did change outcomes sat mostly inside or after the mode, in runs that reported checks as passed with nothing run on the real surface and in merges without the cross-model review, and no trigger reaches those.

Upstream points the same way. Pstack's author added a rule-based reminder to apply the mode when a playbook matches or rigor is needed (cursor/plugins #144), then removed it when Cursor ignored the keys (#597). Addy Osmani removed the hook that preloaded his router on hosts that already route skills by description, because it stacked a second router and cost tokens every session, and he made his commands user-invoked. Matt Pocock keeps every orchestrator user-invoked.

So the mode stays explicit. `/next-options` offers it when an answer outside the mode leads to a code change, where the owner typed it by hand in 15 threads, and picking that option counts as invoking it. The mode's gates reach every path instead: `/pr` makes a missing review or an unverified UI change visible in each PR body, and `/review-loop` runs only the counterpart on a small diff. A routing hook would also be host configuration outside `/usage-review`'s revert loop, run on every prompt, and depend on recognizing delegated sessions, which the existing lookup does by failing open.

Revisit when the offer is picked in more than 80% of the menus that show it over four weeks while the owner still forgets the mode, or when owner-labeled threads show a router at least ten points ahead that catches the misses that changed outcomes. Start then with a first-turn logger that injects nothing, recognizes owner threads positively and fails closed, and acts only on ticket or CI links in client repositories.
