# Coordinate T3 projects from a pinned thread

The user asked on 2026-10-31 to adopt Oliver Cederborg's `coordinator`, which runs a multi-PR project from one pinned T3 Code thread. The library already had two coordinators. /pstack-mode's Orchestrate playbook runs a standing program on any host, and Matt Pocock's /chief-of-staff pursues a long-running goal in one session with a wiki for memory. Neither uses what T3 Code adds: child tasks in their own worktrees, PR watches that wake the thread, timers bound to it, and pending questions that workers ask mid-run. Without those, the user has to come back to check on each worker, and calls arrive scattered across threads.

So `coordinator` is a first-party skill built on Oliver's ideas, like `review-loop`, `next-options`, and `reply-shape` ([ADR 0004](0004-review-across-vendors-and-offer-next-options.md)). It keeps his model: one pinned `◆` thread is the only place the user talks to, a project file is the memory, workers own their branches, two slots bound the builds, and the user gets one decision card at a time. It reaches this library's owners for everything else. Workers run /pstack-mode's playbooks and end at a draft PR whose final review is /review-loop. /swarm's T3 route and model roles set each child's brief and target. Its cards and its list of real calls are self-contained, because /reply-shape and /next-options are user-invoked and load only through their opt-in hook; when active, /reply-shape lays the cards out. Watch events go to Babysit passes, and merges go through Shipping, on the user's go. Oliver's router modes, per-repository merge trust, merge-gate hook, and tower are left out, since this library ships none of them.

Orchestrate stays, because it is sourced Pstack text that runs anywhere. The coordinator restates several of its supervision rules in T3 terms, such as piloting one unit, checking a PR's live state, and retrying by cause, rather than citing a playbook whose host-neutral rules forbid what a T3 coordinator needs: a project script, an hourly heartbeat, and handing watch events to owners. The skill is model-invoked, as upstream's is, so a heartbeat, a worker's completion, or a compaction in a coordinator thread reloads it.

T3 Code replays interval timers missed while the machine slept, so every coordinator timer opens with the user's run gate for interval tasks. Workers on another machine are left out until the user links one.

Revised 2026-11-08: the user linked a second machine, so the coordinator gained placement by what its units need and report-only workers on a machine its own T3 Code server links to; links run one way, so it reaches only those machines.

Revised 2026-11-08: one-PR delivery splits a feature into checked ticket branches while keeping one final merge into the target. Council agreed on direct supervision of ticket writers plus one integrator, preserving the coordinator's slots, startup checks, heartbeat, and question routing. A nested implementation coordinator would hide those workers; extracting a new shared skill would add an owner without being needed for this T3 protocol. The integrator alone changes the integration branch, keeps its history stable while tickets remain, and owns the sole final PR. Whole-feature proof covers its head and target base before merge; close can reuse it when the shipped tree matches. Existing projects retain multi-PR delivery, and implement-spec stays a separate user-invoked executor.

Revised 2026-11-14: the hourly heartbeat becomes a scripted tick, following upstream. An operating-system timer on each machine runs it every 10 minutes and messages the coordinator thread only with news T3 does not deliver, so a quiet check costs no model turn, where the hourly heartbeat took a turn each hour. T3's scheduler cannot run a script without a model turn, so the timer belongs to the machine, declared in its config tool where one manages services.

Revised 2026-11-27: a usage limit moves workers along an instance order. One coordinator, on the owner's second Claude account, wrote itself a standing rule on 2026-11-23 to switch a worker to Codex when that account hit a limit. From then to 2026-11-27 it ran 53 workers on Codex, 50 of them started there: 23 during the account's 5-hour limit on 2026-11-23, and 30, with 65 of the 77 Codex run hours, after it had reset, while the account showed no 5-hour or weekly limit and completed 106 to 164 runs a day. Those workers took about 78% of that week's Codex usage, which stood at 82% used four days before its reset. The owner expects workers to move to another Claude account most of the time. The limit also stopped the coordinator, which the owner moved to another account for two days, so "the coordinator's own account" names no fixed place. So a project records a home instance, and `references/usage-limits.md` gives the instance order: the home, then the same driver's other instances, in a standing rule's order when one gives it, and the other vendor only once a limit holds each of those. The coordinator records each limit with its reset time, and new workers start on the home again after the reset. The other accounts are not unlimited: two of the owner's Claude accounts hit weekly limits on 2026-11-26 and 2026-11-27, so the other vendor stays as the last step.
