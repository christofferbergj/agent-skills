# One-PR delivery

Read at coordinator step 2 when the user requests one final PR, and on each resume of that delivery mode. This reference owns the coordinator's T3 branch protocol; /implement-spec remains a separate user-started workflow. All ticket writers, the integrator, and execution verifiers are direct coordinator children. The coordinator owns planning, canonical-document decisions, timers, watches, and user calls; each worker runs only its bounded task, with no recursive coordinator or ticket dispatch.

## Establish ownership

1. Reuse the accepted goal and ticket graph, or split the goal into bounded tickets with dependencies and checks. Record in Goal: `Delivery: one-pr · integration <branch> from <target>@<base SHA> · integrator <slug>`. Record the user's delivery request under Decisions and include it in every ticket, integrator, and final-review brief. Add a Workers row for the integrator and each ticket; keep the graph and acceptance evidence there rather than creating a second tracker. Complete when every ticket has a proof and each writable branch has one owner.
2. Launch the integrator in its own worktree to create and push the integration branch from that base; it alone writes this branch, canonical repository documents, and the final PR. Ticket branches start from a checked integration SHA, not an assumed worktree base. All writers run on the coordinator's machine; remote workers remain report-only. Complete when the integration branch and checked starting SHA are recorded and ready tickets can name their base.

Use step 3's ordinary task slots, startup checks, and heartbeat for every worker. An integration task takes a build slot and the next free slot ahead of new tickets. While any ticket remains unintegrated, the integrator updates from the target by merge only: preserve integration history, with no rebase or force-push. After all tickets are accepted, history cleanup is allowed before final proof. Any later rewrite invalidates that proof. After cleanup, accepted ticket SHAs remain historical evidence; never replay accepted tickets merely because rewritten ancestry differs.

## Brief variants

Replace both the Build and branch-ownership lines of the standard brief. Paste the applicable variant in full, with resolved paths, SHAs, checks, and Decisions; workers need not discover this reference.

**Ticket writer**:

```text
Build: read <pstack-mode SKILL.md> and run the fitting playbook against this ticket's accepted scope. Start <ticket branch> from integration <branch>@<base SHA>, verifying the actual worktree base. Implement this ticket directly, dispatching no code writers. Request independent execution verifiers or probes from the coordinator; only bounded read-only review delegates are allowed. Stop at a checked, pushed commit; skip Opening a PR and per-ticket /review-loop. Return proposed canonical-document edits for coordinator reconciliation.
Ownership: write only this ticket branch and its scoped files. Before reporting, merge the current checked integration tip into this branch, rerun ticket checks, and push. Report base, result SHA, checks and their outputs. Open no PR, create no stack or watch, and merge nothing into the integration branch or delivery target.
```

**Integrator**:

```text
Build: own <integration branch> and the single final PR into <target>. For each coordinator acceptance task, integrate only its named ticket SHA onto its named checked integration SHA, one at a time. Apply the canonical-document changes the coordinator reconciled, run the named checks, and push only a passing integration revision. Report old tip, ticket SHA, new tip, and check outputs. On a merge conflict or failed integration check, report the outputs, preserve any created merge commit under a local recovery ref, abort any unresolved merge, restore the named checked tip, push nothing, and return the ticket to the coordinator for owner repair.
Ownership: you alone write the integration branch and final PR. While tickets remain unintegrated, bring target changes in by merge only, preserving history without rebase or force-push. On the coordinator's explicit finalize task, after all tickets are accepted, record the pre-cleanup tip, run whole-feature checks and /review-loop, apply in-scope fixes, and recheck affected behavior. When the coordinator requests an early CI draft, open the sole PR explicitly as a draft, deferring Opening a PR's history cleanup and final review until finalize; preserve integration history. At finalize, run Opening a PR with the user's one-PR delivery decision overriding its stack preference, and reuse that draft. Keep the single-PR shape through Babysit and Shipping. The coordinator owns watches and approval to merge into the target; internal ticket integration is authorized by its acceptance task. Implement fixes directly; dispatch no code writers, ticket workers, or recursive coordinator. Request independent execution verifiers or probes from the coordinator, including Shipping verification; bounded read-only review delegates remain allowed. Shipping consumes the coordinator-managed independent runtime verdict for the supplied verified head/base pair instead of spawning another verifier or relying on patch-id reuse. Immediately before merging, reread the live head, target base, and required checks. A head/base mismatch returns to the coordinator for refreshed proof before continuing; wait for its updated verdict.
```

Complete when each launch has exactly one branch owner, its starting SHA, its stopping point, and the delivery decision in its brief.

## Accept tickets

1. Read the ticket's diff and check evidence at its reported SHA. Send any claim requiring execution to a verifier. Reconcile canonical-document proposals through /domain-modeling and send only accepted edits to the integrator. Set a checked ticket to `waiting: integration`, with its result SHA and the integrator as Waits on. Complete when acceptance names the exact result, checks, and approved scope.
2. Send the integrator a self-contained task naming the ticket branch and result SHA, expected checked integration tip, accepted doc edits, required checks, and decisions since its last task. If the actual tip differs, reconcile it before integration. On a conflict or failed integration check, require the recovery report and unchanged checked integration tip, then assign repair to the ticket writer with the failed outputs and preserved result. The writer merges the checked integration tip and reruns checks; inspect the new result again. Complete when the integrator reports a pushed, passing integration SHA or a named repair task.
3. Verify the report against the diff and commit ancestry. Record `done: integrated at <SHA>` on the ticket, its result SHA, the integrator's new checked tip, and the internal merge order under Decisions. Freeze accepted ticket branches; later fixes go to the integrator or a fresh fix ticket based on its current tip. Start dependents only once their required integration evidence exists. A shared-brief ticket pilot is proven by its checked integration, before siblings start. When all required tickets read `done: integrated`, send an explicit finalize task listing accepted ticket SHAs, integration order, checked tip, approved scope, delivery decision, whole-feature checks, and final review requirements. The integrator ends that task at its whole-feature code-ready report and single draft PR. Complete when each accepted ticket is traceable to its integration commit, every ready dependent is scheduled, and, once every required ticket reads `done: integrated`, the finalize task has been sent.

On resume, reconcile recorded bases, results, integration ancestry, task states, and PR state before redispatch. A replacement integrator starts only after its predecessor and any writers in its worktree have ended and their local work is accounted for; assign a recovery worker temporary sole ownership of the stopped owner's worktree to preserve unpushed commits and local changes on a named salvage branch, reporting its SHA and remaining local state, before the replacement uses the recorded remote tip. The recovery worker leaves the integration branch unchanged and ends before replacement starts. Name the salvage ref in the replacement brief. Mark the predecessor replaced, update the integrator slug in Goal, and transfer sole branch ownership explicitly. Complete a resume when exactly one integrator owns the reconciled tip and every ticket is queued, running, waiting on named work, or accounted for at an accepted SHA.

## Prove and ship

The integrator may open the sole draft PR early for CI. Start its PR watch only after all tickets are accounted for and the whole feature is code-ready. Route every watch event, review fix, and Shipping task to the integrator. A fresh fix ticket reopens the acceptance cycle; refresh final proof afterward.

Before offering the final merge, require the integrator's Clean /review-loop and a separate verifier subthread proving the whole goal at the final PR head and current target base. The verifier uses an isolated worktree, combines that exact head with that exact base locally, runs whole-feature checks, and reports both SHAs, the tested tree, checks, and outcomes; it merges nothing on GitHub and does not reassemble ticket branches. Require Shipping's independent runtime verification, parent against head through the actual user path, as part of this verifier's brief; it returns PASS, PASS+NOTES, or FAIL with its evidence. The verifier writes its own report. Record the checked SHAs, tested tree, verdict, and report path in its Workers row and under Decisions. Every fix, history rewrite, or target-base change requires refreshed affected checks and final-artifact verification; review coverage follows /review-loop at the final artifact.

Read the live PR head, target base, and checks before offering the merge. Send the integrator a Shipping task carrying the user's go, verified head and target-base SHAs, tested tree, independent verdict and report, and the requirement to stop for refreshed coordinator-managed proof on any mismatch. Its execution-time gate is part of the integrator brief above. A draft whose required CI starts only when marked ready may get a conditional approval card only after local whole-feature proof and review; Shipping must wait for green required CI and revalidate the artifact before merging. If head or base changes, re-prove it before continuing. The user's go authorizes only the final PR into its target, unless a standing rule already grants it.

Complete when the single PR shows MERGED, the shipped tree is checked against the verifier's tested tree as [phase end and close](#phase-end-and-close) describes, and all ticket branches remain implementation history rather than separate deliveries.

## Phase end and close

Read at a [phase](phases.md) end and at the [close](close.md).

- **Phase-end check**: when the integration branch holds unmerged work, run [prove and ship](#prove-and-ship)'s verifier at the branch's checked tip, or the final PR's head once it opens, and the current target base. Reuse a proof already recorded at those same SHAs. Record the SHAs, tested tree, and verdict under Decisions.
- **Carry**: the integrator stays `waiting` on the integration branch, or on its PR once one opens. Tickets at `waiting: integration` keep that state. The accepted tickets' SHAs, the merge order, and the latest whole-feature proof stay in the ended phase's archive; read them there for the finalize task, the merge card, and the close.
- **Close**, by the final PR's state, reading the proof from Decisions, its verifier's row, or a phase's archive. Never combine the ticket branches again, and record the proof and any tree comparison under Result.
  - **Merged**: compare the merge commit's tree with the verifier's tested tree; a squash merge changes commit SHAs, so tree equality decides reuse. Reuse the evidence only for the same tree and checks. Otherwise start a fresh isolated verifier at the shipped merge commit, running the whole-goal checks and reporting the difference; any failure remains open for repair or an explicitly accepted limitation.
  - **Open**: reuse the proof only at the PR's current head and target base, and otherwise run the verifier again at them.
  - **No PR**: ask the user in one decision card whether to open the final PR first, as prove and ship does, or close with the integration branch unshipped. Unshipped, record the branch, its checked tip, the target base, and the latest proof at those SHAs, reusing one or running the verifier again, and give the integrator `dropped`.

Complete a phase end when its check passed or no work was unmerged and the integrator and tickets carry; complete a close when Result holds the merged tree's comparison or shipped-commit verification, the open PR's proof at its current head and base, or the unshipped branch's record.
