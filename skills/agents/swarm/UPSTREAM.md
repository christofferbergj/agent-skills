## Local adaptations to preserve

Each divergence names the reason under the owner's rule on #113 that keeps it.

- The [library-wide adaptations](../../agents/maintain-skills/references/ADAPTATION.md#library-wide-adaptations) apply; this list holds only this skill's own divergences.
- Local-only files: `references/execution.md`, the host execution contract that replaces Cursor's Task-tool and model-rule mechanics; `scripts/review.py` with its tests, the bounded cross-vendor CLI wrapper; `scripts/target.py` with its tests, which resolves each role's and panel seat's model, effort, and speed from the personal configuration, with the remaining Codex usage stepping down Codex targets; `scripts/reset_guard.py` with its tests, which redeems a banked Codex reset before it lapses unused; and `references/computer-use.md`, which hands checks that need Computer Use from Claude to Codex. Reason 1.
- Phase A step 3 and Phase B translate the `swarm workers` rule line, Cursor's Task fields, cloud environment, and `cloud_base_branch` through the execution contract and upstream's Claude Code mapping: the `swarm-workers` role, native background agents isolated in worktrees, and a brief that names the branch to check out. Phase B also sends a job that needs another machine through the T3 route. Reason 1.
- Panels keep upstream's three seats: Fable and Opus at `high`, and Gemini 4 Neon at `xhigh`, which runs only through T3 Code's Antigravity provider and so carries a Codex fallback at its effort, native in Codex and the counterpart in Claude Code. Fable and Opus are native in Claude Code and run on the Claude counterpart in Codex. Reason 1.
- No role or counterpart runs above `xhigh`: upstream's ceiling extends to the counterpart's review and Computer Use efforts, by the owner's answer on #113. Reason 1, since the counterpart is the T3 route's other vendor.
- Match review briefs to the restricted reviewer's readable scope. Supply recorded checks and inline snapshots for inaccessible evidence; use a native critic when independent execution or broader evidence access is required. Reason 1.
- Route counterpart critics through T3 Code child tasks when the session exposes `delegate_task`, before the CLI wrapper, and pass the resolved target's model, scope-scaled effort, and speed on every route ([T3 route](references/t3.md)). The T3 route is principle-derived from the second source below. Reason 1.
- Add the local `long-running` role to `scripts/target.py` for threads that run for hours, such as a /coordinator thread and its workers, so personal configuration can keep them off a model with a tight weekly allowance. It is principle-derived from the second source's 07eabc8. Reason 1.

### Local adaptations to preserve

Adopted principles: cross-provider critics run as tracked T3 child tasks; `orchestrator_capabilities` runs once per thread, before the first `delegate_task`; every call names the model and effort; the brief is the child's whole context and passes files by absolute path; a stable `clientRequestId` per task; read-only critics in plan mode, titled with what they review, the round, and the model; a critic returns findings as its final message, and a writer returns a short report naming a file; a finished child wakes this thread, so the coordinator keeps working or ends the turn instead of polling; a failed optional critic is reported, and the work continues without it; a child goes to a linked machine when it would load this one for long, and everything it reads is pushed; an unreachable machine means running here and saying so; a child there is a top-level thread, waited on with `t3_thread_wait`, read with `t3_thread_read`, both with its `environmentId`, and settled with `t3_thread_organize` once read.

Departures: orchestrate's Notes line is left out, under /review-loop's departure for addystack's per-user notes; the counterpart's model, effort, and speed come from `scripts/target.py`, which reads the personal configuration and the remaining Codex usage, not a role table of writers and sketchers; a usage-limit failure skips the retry and every route on that vendor's account; a new key for each retry attempt; collection through a repeated `wait` call that never blocks on an unfinished child, where upstream gives the wait 30 minutes, because T3 Code caps it, as [the T3 route](references/t3.md) says; T3 is the first of three routes, ahead of the CLI wrapper and a native critic; Oliver's owner threads, coordinator workers, report-file paths, thread-paging rules, and eval players are left out. On another machine, a child starts as a `t3_thread_launch` thread, in a worktree on a pushed branch when it checks out, where upstream sends a `delegate_task` child into that machine's root checkout and runs one per project at a time, because `t3_thread_launch` with `environmentId` is what was tested here and a worktree removes the shared checkout and its queue; its report comes in its final message, where upstream reads a file with `ssh <machine> cat`, because their Linux server cannot ssh into the Mac; load alone sends a child only to a machine other than the user's laptop, since the Mac can sleep; and off a Mac, the Computer Use route runs its check on a reachable linked Mac when this thread and the link allow full access, resolved with `target.py --on-mac`, before any fallback.

Decide upstream changes to these files by the principle-derived rules. The 2026-10-20 import adapted the T3 section and guide; plan-mode children of both vendors and a repeated `wait` call collecting an async child were exercised in T3 Code, and the CLI wrapper's model and effort flags pass unit tests and a preflight on both real CLIs.
