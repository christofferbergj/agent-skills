# T3 Code child tasks

T3 Code runs a task on another provider as a tracked, cancellable child of the current thread. Inside T3 Code, run counterpart critics and Computer Use delegates this way rather than launching the other CLI from a shell, which T3 cannot show or stop.

## Choose the target

Load `orchestrator_capabilities`, `delegate_task`, and `task_status` together; in Claude Code that is one `ToolSearch` with `select:`. Call `orchestrator_capabilities` once per thread, before the first `delegate_task`, as T3's own orchestration instructions say; it lists the provider instances, their models, and each model's options. Resolve the target as the execution contract describes, then:

- Use the target's `providerInstanceId`, or the instance whose driver is the target's vendor: `codex`, or `claudeAgent` for Claude. When several instances share that driver, use the one whose `providerInstanceId` equals the driver name, and disclose the choice.
- Always set `providerInstanceId`, `model`, and the effort option, which is `reasoningEffort` for Codex and `effort` for Claude. For Codex, also set `serviceTier` when the target has one. For Claude, set `fastMode` to `false` when the model lists that option. A provider switch without a model takes its first listed model.
- The listing is short. To find the newest Opus model, or a chosen model the listing lacks, pass `search` on that one call. Call it again only after an error, such as `delegate_task` failing with `model_unavailable`, or when the user names another provider; then retry once with a listed model.

## Dispatch

- `task` is the complete brief. The child sees only this text, never this conversation, so pass files by absolute path. State that its final message is a report to the coordinating agent, without the user's reply conventions such as lettered next options.
- A read-only critic gets `role: "review"`, `interactionMode: "plan"`, and a `title` naming what it reviews, its round, and its model, such as `◎ #312 r1 · gpt-6.1-terra`, and its brief still states the read-only limits. In plan mode, children of both vendors can read files outside the repository and run read-only commands without approval prompts. Claude Code also saves each plan-mode session's plan under `~/.claude/plans`; that host file is expected and is not a write by the critic.
- A writer, such as an /arena runner, gets the `role` that fits its work, such as `design` or `implementation`, and the default interaction mode. Its brief names its own output location outside the parent's checkout, and a writer that edits code gets `isolation: "worktree"`.
- `clientRequestId` identifies one task: repeating it returns that task instead of starting another. Reuse it to collect a result or to resend a request whose response was lost. A new attempt after a failed child and each new review round need a new key, such as the round's key with `-retry-1`. A new round is a new `delegate_task` carrying the original brief, prior findings, and responses, so the critic reviews the delta fresh; a send to the old child's thread would continue that child's conversation instead.
- `mode: "async"` keeps the coordinator working while the critic runs. To collect the result, call `delegate_task` again with the same `clientRequestId` and `mode: "wait"`: it returns the same task and blocks until the child finishes or `timeoutMs` passes. Give a critic's wait `timeoutMs: 1800000`, since a full review often outlasts the ten-minute default. After `waitTimedOut: true` the child keeps running, so read `task_status` once later instead of polling.
- When `hasPendingQuestion` is true, answer from the brief through `t3_pending_request` `respond`, or report the question.

## Results and failures

The child's final message is its result. It returns as `summary` and stays in this thread's context, so a critic returns findings only, and a writer writes long evidence to a file and returns a short report naming it. Read a child's thread with `t3_thread_read` only for what the summary lacks.

When a child fails on authentication, timeout, or a provider error, retry once under a new key when the execution contract allows a retry. Then take the next route it allows and disclose the missing pass; a failed child is a gap, never a pass.

## On another machine

The **linked machines** are the ones this T3 Code server links to: `t3_environment_links` lists them, each with whether it answers now, and when the session doesn't expose that tool, `"$(command -v t3 || echo ~/.t3/bin/t3)" environment list --json` in the shell gives the same list with each machine's `environmentId` and `status`. A link runs one way, so a child can go only to a linked machine. Send a child there when it needs something only that machine has, such as a macOS desktop, or when it would load this machine for long and that machine isn't the laptop the user works on, and only when everything it reads is pushed or in its brief. When the machine isn't `reachable`, run the child here, or take the calling route's fallback when only that machine can run it, and say so in the report.

- **Launch**: `t3_thread_launch` with the machine's `environmentId`, a stable `clientRequestId`, the brief as `message`, and the target in `modelSelection`: the provider instance as `instanceId`, the model, and the effort and speed `options` as `orchestrator_capabilities` with that `environmentId` lists them, since that machine's instances and option ids can differ from this one's. A retry is a new launch under a new key, such as `<key>-retry-1`; the same key returns the first thread. Take `projectId` from `t3_project_list` with that `environmentId`, since this machine's project ids don't exist there, or pass `scratch: true` for a child that needs no checkout. A child that checks out, builds, or writes gets a `worktree` `workspaceStrategy` on a pushed branch, since unpushed commits stay here.
- **Report**: this machine can't open files there, so the brief asks for the whole report, with the path of each piece of evidence on that machine, in the child's final message.
- **Wait**: `t3_thread_wait` on the child's thread with its `environmentId`, ending the turn when a timed-out wait returns `next`. Then read its last message with `t3_thread_read` and the same `environmentId`.
- **Continue**: send an answer or more work to a finished child with `t3_thread_send` and its `environmentId`.
- **Settle**: the child is a top-level thread in that machine's sidebar. Once you've read its result, settle it with `t3_thread_organize` `settle` and its `environmentId`.
