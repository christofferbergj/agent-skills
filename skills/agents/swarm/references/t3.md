# T3 Code child tasks

T3 Code runs a task on another provider as a tracked, cancellable child of the current thread. Inside T3 Code, run counterpart critics and Computer Use delegates this way rather than launching the other CLI from a shell, which T3 cannot show or stop.

## Choose the target

Load `delegate_task` and `task_status` together; in Claude Code that is one `ToolSearch` with `select:`. Resolve the target as the execution contract describes, then:

- Use the target's `providerInstanceId`, or the instance whose driver is the target's vendor: `codex`, or `claudeAgent` for Claude. When several instances share that driver, use the one whose `providerInstanceId` equals the driver name, and disclose the choice.
- Always set `providerInstanceId`, `model`, and the effort option, which is `reasoningEffort` for Codex and `effort` for Claude. For Codex, also set `serviceTier` when the target has one. For Claude, set `fastMode` to `false` when the model lists that option. A provider switch without a model takes its first listed model.
- Call `orchestrator_capabilities` only to find the newest Opus model, when the chosen model is missing, or after `delegate_task` fails with `model_unavailable`; then retry once with a listed model.

## Dispatch

- `task` is the complete brief. The child sees only this text, never this conversation, so pass files by absolute path. State that its final message is a report to the coordinating agent, without the user's reply conventions such as lettered next options.
- A read-only critic gets `role: "review"` and `interactionMode: "plan"`, and its brief still states the read-only limits. In plan mode, children of both vendors can read files outside the repository and run read-only commands without approval prompts. Claude Code also saves each plan-mode session's plan under `~/.claude/plans`; that host file is expected and is not a write by the critic.
- A writer, such as an /arena runner, gets the `role` that fits its work, such as `design` or `implementation`, and the default interaction mode. Its brief names its own output location outside the parent's checkout, and a writer that edits code gets `isolation: "worktree"`.
- `clientRequestId` identifies one task: repeating it returns that task instead of starting another. Reuse it to collect a result or to resend a request whose response was lost. A new attempt after a failed child and each new review round need a new key, such as the round's key with `-retry-1`. A new round is a new `delegate_task` carrying the original brief, prior findings, and responses; sending to the old child's thread starts a run without that brief.
- `mode: "async"` keeps the coordinator working while the critic runs. To collect the result, call `delegate_task` again with the same `clientRequestId` and `mode: "wait"`: it returns the same task and blocks until the child finishes or `timeoutMs` passes. After `waitTimedOut: true` the child keeps running, so read `task_status` once later instead of polling.
- When `hasPendingQuestion` is true, answer from the brief through `t3_pending_request_respond`, or report the question.

## Results and failures

The child's final message is its result. It returns as `summary` and stays in this thread's context, so a critic returns findings only, and a writer writes long evidence to a file and returns a short report naming it. Read a child's thread with `t3_thread_read` only for what the summary lacks.

When a child fails on authentication, timeout, or a provider error, retry once under a new key when the execution contract allows a retry. Then take the next route it allows and disclose the missing pass; a failed child is a gap, never a pass.
