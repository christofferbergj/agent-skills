1. Read the configured project artifacts through /domain-modeling and reuse any accepted spec and ticket graph. Inspect the existing system and name the data shape, user path, invariants, and done predicate. Invoke /pstack-how where unfamiliar. Complete when implementation has a grounded boundary and measurable result.
2. For consequential interfaces use /pstack-architect; use /pstack-arena when competing shapes would materially change the outcome. Build a cheap prototype to settle empirical forks rather than asking the user to guess. Complete when the selected shape fits the scope and any requested approval exists.
3. Plan useful independent units and a verification checkpoint. Delegate through /pstack-swarm where it helps, with isolated writers and explicit contracts. Complete when every unit has an owner, output, and check.
4. Implement the smallest sufficient behavior through /tdd at accepted public seams when a practical test path exists. Reconcile accepted domain changes through /domain-modeling. Use relevant principle owners, inspect delegated changes, and avoid preserving obsolete internal APIs. Pause before changing approved scope or interfaces. Complete when the implementation matches the agreed behavior.
5. Run applicable unit and integration checks and drive the real user path using the repository's verification skill or available control tools. Preserve before/after evidence, including durable side effects. Use /pstack-benchmark-checklist for performance claims. Complete when required surfaces have evidence or an explicit unresolved gap.
6. Invoke /code-review for the final Standards/Spec assessment; add /pstack-interrogate only when an adversarial lens is warranted, reusing equivalent current evidence, apply /pstack-no-comments, and prepare the result through Opening a PR when authorized. Complete when the final committed artifact and reported evidence agree.
